Language of payment systems:
ISO 8583 protocol

Payment Systems · Interactive

Do you want to walk through a real message directly?

Walk through a real message

Payment machines like ATMs and POS terminals, the ones where you tap your card over NFC, don't speak the HTTP that 99% of software engineers are used to.

Then how do they talk?

Well, most payment machines follow an old 1987 format called ISO 8583 to encode the message and send it over a raw TLS connection, not HTTP!

An HTTP request has a path, a verb like GET or POST, and a JSON body. An ISO 8583 message has none of those. So what does it have instead?

Let's find out by poking at a real one. Everything below is clickable.

Where does NFC fit in? The tap only happens between your card and the terminal, over a few centimetres. That hop speaks APDU commands. How Google Wallet talks over NFC opens that conversation. After the tap, the terminal packs what it learned (card number, amount, its own ID) into an ISO 8583 message and sends it to the bank. That message is what we're opening up here.

1The same sale, in two languages

Here is a 150.00 card sale written both ways. Flip between them.

Same information, but the ISO 8583 version has no field names, no quotes, no braces and no path. In 1987 these messages travelled over slow modem lines where every byte cost time and money, so the format sends only the values, in positions both sides agreed on beforehand.

So where did everything HTTP gives you go?

That length prefix matters more than it looks. A TLS or TCP connection is just a stream of bytes with no message boundaries. HTTP solves that with Content-Length. A raw ISO 8583 link solves it by starting every message with its own byte count, so the receiver knows exactly how many bytes to read.

2The trick: numbered boxes

Imagine a paper form with 128 numbered boxes. Box 2 is the card number. Box 4 is the amount. Box 41 is the terminal ID. ISO 8583 calls the boxes data elements, or fields.

A message never says the word "amount". It just fills in box 4. Every system that speaks ISO 8583 owns the same numbered form (the spec), so the number is enough. These are the boxes our sale will use:

A message fills only some of the boxes, so the receiver needs a way to know which ones. That is the bitmap, and we'll get to it. First, a one-minute detour, because everything from here on is measured in bytes.

3Bits, bytes and hex in one minute

The wire carries bytes, and one byte is 8 bits. Raw bits are painful to read, so logs print each byte as two hex characters.

Why two? One hex character (0 to 9, then A to F) has 16 possible values, which is exactly 4 bits. Two of them make 8 bits, one byte. Click the bits to see it:

Text works the same way: every character is one byte (its ASCII code). Type something:

Remember this line. 1 byte = 8 bits = 2 hex characters. So a 64-bit bitmap is 8 bytes, which prints as 16 hex characters.

In a real log you'll see something like 703C468008C09000. The terminal never sent those characters. It sent 8 raw bytes, and the logging tool printed each byte as a pair of hex digits.

4Walk through a real message

This is what a terminal sends for a 150.00 sale, as it appears in a log: one long string, with no separators. The message does not mark its own boundaries. Both sides know the rules, so we read it left to right: finish one piece, and it tells us where the next one starts.

Press Start, then Next piece. You can also click any piece you've already passed.

Three things to notice

  • The first four pieces (length, transport header, message type, bitmap) have sizes you must know in advance. They come from the interface spec for your connection, not from the message.
  • Only the card number carries its own length. Everything else has a size fixed by the spec.
  • Numbers are packed as BCD (each hex digit is one decimal digit, so 4111 is simply the digits 4, 1, 1, 1). Text fields are ASCII, which looks like gibberish until you read each pair as a character. The spec says which is which.

5The bitmap: the message's table of contents

The bitmap has one bit per box. A 1 means "this box is filled in this message". Sixty-four bits cover boxes 1 to 64, which is 8 bytes. Each row below is one byte, and its hex value is shown on the left. Click boxes to switch fields on and off:

Bitmap as it would appear in a log

Why is the first hex character usually 0 to 7?

Bit 1 is not a field. It means "a second bitmap follows". The first hex character holds bits 1 to 4, and bit 1 is its leftmost bit, worth 8.

  • Bit 1 off (no second bitmap): the first character is 0xxx in binary, so 0 to 7.
  • Bit 1 on (second bitmap follows): the first character is 1xxx, so 8 to F, and 8 more bytes of bitmap cover fields 65 to 128.

Every other character of the bitmap can be anything from 0 to F. Try it above: switch on box 1 and watch the first character jump to 8 or higher.

6Build your own message

Change the card, amount or IDs. Watch the bytes change, and notice that the length prefix updates by itself.

PieceHexBytes

Try a short terminal ID such as T1: it gets padded with spaces (hex 20) so the field stays exactly 8 bytes. Fixed sizes are the whole point.

7The recipe, in four steps

  1. Cut the front. Length prefix, transport header, message type and bitmap are fixed sizes from the spec. Count the bytes.
  2. Read the bitmap. Each 1 is a field that is present. If bit 1 is on, another bitmap follows.
  3. Read each field in order. The spec gives each one a rule: a fixed size, or a length in front of it. Finish one, and you know where the next starts.
  4. Check your work. The bytes you consumed after the prefix must equal the number in the prefix, with nothing left over. If not, the first garbled field points at the one before it, where your count went wrong.
Real networks differ. This message uses one common layout. Others use ASCII numbers instead of BCD, a different header, a 4-digit length, or a second bitmap. The rules above never change, but the interface spec for your connection decides every size. Everything here is made up for teaching: the card is a well-known test number and the PIN block is a dummy.
