1First, understand the three terms

Imagine you have:

  • A POS terminal with an NFC reader.
  • A phone with Google Wallet, already unlocked.
  • You hold the phone to the terminal.

Three technologies carry that tap.

TermMeaningPurpose
APDUApplication Protocol Data UnitThe actual commands and responses
ISO-DEPISO 14443-4Transports APDU messages between devices
NFCNear Field CommunicationProvides the wireless connection

Think of it like this:

  • NFC = the wireless connection.
  • ISO-DEP = the delivery mechanism.
  • APDU = the actual message being delivered.

They are different layers of the same tap. APDU sits on top. NFC is the bottom.

APDUThe command, or the answer.
ISO-DEPCarries that message across.
NFCThe radio, a few centimetres.

2Who is communicating with whom?

Two roles. The terminal starts every command. Google Wallet only answers, and it answers as a card.

The POS starts the APDU conversation. During the tap it cannot tell that the card is a phone.

3What happens when you tap?

Three stages. Payment commands start only at the last one.

A · NFCThe terminal finds the phone and wakes it as a card.
B · ISO-DEPThey agree how to carry longer messages.
C · APDUThe terminal gives orders. Google Wallet answers.

Stage A: NFC connection

The POS detects the phone and establishes a connection.

Some lower-level NFC messages discover the phone and activate it. No card has been chosen yet.

Stage B: ISO-DEP activation

The POS and the phone establish ISO-DEP.

  • RATS: the reader asks to activate ISO-DEP.
  • ATS: the phone responds with its capabilities.

Google Wallet does not see these two messages.

Stage C: APDU communication

Now the payment conversation begins.

The POS sends APDU commands. Google Wallet responds.

4What does an APDU message look like?

An APDU is basically a byte array.

For example, the POS might send this SELECT command. Each slice is one part of the order:

00CLA A4SELECT 04by name 00first match 077 bytes follow A0000000031010Visa AID 00send the answer
BytesMeaning
00CLA – command class
A4INS – instruction (SELECT)
04P1 – selection method
00P2 – selection options
07Lc – length of following data
A0000000031010AID – application identifier
00Le – expected response length

In simple language, the POS is saying:

"Google Wallet, select the Visa application named by this AID."

Google Wallet processes the command and responds.

For example:

6F ... 90 00

Here:

  • 6F ... = application information.
  • 90 00 = successful execution.

90 00 is a common APDU success status.

5What does ISO-DEP actually do?

You might wonder: why do we need ISO-DEP if we already have APDU?

A reply can be hundreds of bytes. NFC can only carry a short block at a time.

ISO-DEP handles things such as:

  • Splitting larger messages into multiple blocks.
  • Reassembling received blocks.
  • Handling acknowledgements and retransmissions.
  • Managing communication flow.
BlockPurpose
I-BlockCarries actual information
R-BlockAcknowledgement / retransmission
S-BlockControl operations

Google Wallet never sees the blocks. The phone rejoins them and hands Google Wallet one whole APDU.

6What Google Wallet and the POS say

A simplified tap looks like this. Every line is one APDU, carried by ISO-DEP.

POS → Google WalletSELECT PPSE. Which cards can you pay with?
Google Wallet → POSVisa's applications on this phone:
  • Visa credit/debit A0000000031010
  • Visa Electron A0000000032010
  • V PAY A0000000032020
  • Visa Interlink A0000000033010
POS → Google WalletSELECT AID. Use this card.
Google Wallet → POSThat card is selected.
POS → Google WalletGPO. How do I process this sale?
Google Wallet → POSRead these records. Here is what I support.
POS → Google WalletREAD RECORD.
Google Wallet → POSThe card data.
POS → Google WalletGENERATE AC. Build a cryptogram.
Google Wallet → POSA one-time proof. Not an approval yet.

The exact sequence depends on the card network. The number in the card data is usually a token: a stand-in for the real card, issued for this phone. The printed number does not cross the radio.

The cryptogram is not an approval. The terminal still has to ask the bank. That second conversation is not NFC.

Let's start the lessons

Three commands. Each one is a single APDU. The terminal sends it. Google Wallet answers.

Lesson 1: SELECT PPSE

First, what is PPSE?

PPSE = Proximity Payment System Environment

Think of PPSE as the menu of cards in Google Wallet.

For example, Google Wallet might offer these Visa applications. A phone returns only the ones actually in the wallet. A0000000031010 is the usual Visa tap.

  • Visa credit/debit A0000000031010
  • Visa Electron A0000000032010
  • V PAY A0000000032020
  • Visa Interlink A0000000033010

When you tap, the POS does not yet know which card Google Wallet will offer.

So it asks:

"Which cards can you pay with?"

Step 1: POS sends SELECT PPSE

The POS sends this APDU. The long slice is a name, not a card number:

00 A4 04 00SELECT by name 0E14 bytes 2PAY.SYS.DDF01the PPSE name 00send the answer 
00 A4 04 00 0E 325041592E5359532E4444463031 00

What did we achieve?

The POS now knows which of Visa's applications Google Wallet can pay with. It has not chosen one. The usual choice is A0000000031010.

Lesson 2: SELECT AID

Now the POS must choose one application.

For example, it chooses Visa.

It sends:

00 A4 04 00 07 A0000000031010 00

Here:

A0000000031010

is the Visa AID.

Google Wallet receives this APDU and selects that card.

It responds with its application information (FCI).

For example:

6F ... 90 00

The actual response contains application-specific data.

What did we achieve?

The POS has selected the Visa card inside Google Wallet. Google Wallet did not choose it. The POS did, from the list it was just given.

Lesson 3: GPO

Now things get interesting.

GPO = Get Processing Options.

The POS asks the selected payment application:

"Tell me how to process this transaction. Which records should I read, and what processing capabilities do you have?"

The POS sends:

80 A8 00 00 02 83 00 00
PartMeaning
80CLA
A8GPO instruction
00P1
00P2
02Data length
83Command template
00Empty PDOL data
00Expected response length

This is a simplified example where the application has no PDOL requirements.

In a real tap, Google Wallet can ask for transaction information through PDOL, such as:

  • Amount
  • Transaction currency
  • Transaction date
  • Terminal country
  • Transaction type

The POS supplies those values in the GPO command.

Google Wallet responds with information such as:

  • AIP (Application Interchange Profile)
  • AFL (Application File Locator)

These tell the POS what the application supports and which records to read.
