1 Beginner

HTTPS protects the road, not every stop

TLS keeps strangers from reading traffic between the phone and the first server it reaches. That first server is usually a CDN, a WAF, or a load balancer, and the TLS connection ends there. From that point the request travels through your network as plain JSON.

Every stop on the way can read the body. Request logs, error trackers, and crash dumps often save it. A PIN that is readable at any of those stops is exposed to everyone who can read them.

Encrypting the PIN on the phone with a public key changes this. Only the hardware security module (HSM) that holds the private key can open it. Switch between both modes and type your own PIN.

    2 Beginner

    What actually gets encrypted: the PIN block

    A four digit PIN has only 10,000 possible values. If you encrypted the bare digits, everyone who chose 4821 would produce the same ciphertext, and a captured value could be replayed on another card.

    The ISO 9564 PIN block fixes this by mixing the PIN with the card number before encryption. Format 0 builds two 16 digit hex strings and XORs them. Change the card and the block changes, even when the PIN stays the same.

    Lab 2 · Build a format 0 PIN block

    In production this happens inside the HSM or the PIN pad, never in app code on a server. Format 3 swaps the fixed F padding for random values, and format 4 is the AES version. Because the block is tied to its card number, a copy of it is not useful on another card.

      In transit, treat PAN, expiry, and CVV like the PIN and encrypt the payload, because TLS ends at your gateway. Whether Google Wallet needs the CVV depends on the flow.       4 Intermediate

      Encryption keys and rotation

      A common fear is that rotating the key makes old data unreadable. It does not, as long as every row remembers which key encrypted it. You add a new key for new rows and keep the old keys for reading.

      The lab uses real AES-256-GCM in your browser. Rotate the key, store a few rows, and decrypt the old ones. Then delete a key that rows still use and see what happens.

        5 Intermediate

        Where the keys live

        Encryption only helps when the key is somewhere else. A key stored in the same database, or in a config file on the same server, goes with the data when someone copies it. Envelope encryption keeps the keys out of reach in three steps.

        1. Generate a data key and use it to encrypt the PAN with AES-256-GCM.
        2. Ask the KMS or HSM to wrap that data key with a master key that never leaves it. Store the wrapped key and the key id with the row.
        3. To rotate the master key, re-wrap the small data keys. The PAN ciphertext never changes.

        Lab 5 · Steal the database

        Keys in a config file are better than keys in the database, but anyone who can read the server environment can still read them. A KMS or HSM keeps them off the application host too. MySQL tablespace encryption (TDE) does not replace this. It protects stolen disks, not people with database access.
